# AI 设置保存事务中止专项复跑

复审基线为 `b4fdc52d0e358063b723007050da472735b85841`。代码及回归用例锁定在 `9b10af98e63aed07c8a285f2c1a49b80e8428a77`。

## 修复前后的实际表现

原独立审查在已成功保存一次后更改渠道名称和密钥，再中止下一笔协调事务。桌面和手机都曾出现错误提示，但新配置和新密钥实际已写入，两个同步标记不一致，保存按钮禁用，刷新后再次保存仍然失败。桌面在同一事务中用 `add()` 写入重复主键，浏览器原生 `ConstraintError` 也触发了相同结果。

同一组原始脚本在修复提交上逐字节复用。三次均命中注入故障，渠道恢复为首次成功保存的名称，旧密钥恢复到原持久位置，会话位置仍为空。两处标记一致，按钮可以重试，刷新后的新编辑保存成功。三次记录的模型 POST 请求均为零。[修复前后实测、脚本及校验值](commit-abort-evidence.zip)

## 提交与恢复

- `AiConnections.tsx` 在第一处业务写入前登记原配置和受影响密钥的两个存储位置。只有 IndexedDB 报告整个事务完成，才更新已保存基准、清理修改标记并提示成功。
- `aiDraftMerge.ts` 协调写入和失败恢复。恢复前复核最新 IndexedDB 记录和当前可见标记。成功回滚使用一对新且相等的同步标记发布恢复后的状态，避免其他标签误把旧缓存当作当前值。协调数据库仅保存随机标识和时间。
- 如果配置或密钥写不回，界面说明需要核查的对象并保留编辑。重试时在内存中辨认本次留下的值，重新读取另一标签的实际配置和密钥状态，照常合并独立编辑或提示同字段冲突。
- 新版本即使恢复同步标记再次失败，刷新后仍可根据标记与上次提交的关系重新保存。旧版遗留的无关联标记无法证明先后，玩家可按提示关闭其他设置标签页并点「放弃修改」。该步骤再次核对原标记，仅对齐同步元数据并重新读取实际值。
