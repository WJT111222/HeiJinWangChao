## 请求、候选与结算如何绑定

1. 手动阶段和协调器在现有回合锁内读取正式存档。游戏界面把载入时的实例身份传入工作流。首次生成或明确重做正文时，读取当前世界书，分配独立 UUID，在 V4 书库中保存基础资料。旧候选继续保有自己的快照直到新结果成功保存。
2. 成功正文和可重试的失败记录走同一个候选保存入口。来源凭据与草稿在主库同一个 IndexedDB 事务中写入。该事务检查原草稿、正式修订、实例与请求开始时的时间线 epoch。正文指纹涵盖回合、行动、来源修订、状态、完整候选、截断原文及对应的 Story 失败记录。下游候选的变化不会使原正文失效。
3. 本地凭据记录生成 UUID、实例、存储命名空间以及两个 SHA-256 指纹。世界观指纹包含开关、玩家书版本及常驻资料，并绑定已启用官方模块的发布内容哈希。重试、续写、下游补算先核对原正文和原快照，完成后才允许改写草稿或发送请求。预览正式下游提示词同样读取已核验的快照。
4. 首次结算额外读取独立书库，再在正式写事务里复核来源凭据、草稿及领域校验。已有提交回执保留原有幂等语义。正常结算、覆盖导入和删除会清理相关资源。新生成时按存档清理旧记录，并保留尚未被替换的本地候选。取消时清理未发表的独立 UUID，浏览器突然中断留下的孤立行在该存档下一次捕获时回收。
5. 历史节点恢复及覆盖导入建立新实例。撤回和行动重绑沿用正式工作流创建的新草稿。即使回合号、正文修订、实际文字完全相同，旧请求也必须通过实例、时间线和草稿比较才能写回。世界书设置与已安装版本位于其他对象仓库。

## 数据兼容与恢复

独立书库保持 V4，正式存档库保持 V5。`GameState`、正式草稿、标准备份和领域命令的结构均沿用原版本。唯一新增的主库数据是 `saveControls.storyOrigin` 可选本地字段。独立书库与正式存档分属两个数据库，单靠书库中的计数键无法原子证明正式候选选中了哪次请求。

旧 Beta 存档和备份仍可读取。普通备份只携带正式状态和可导出的草稿，本机来源凭据随实例作废。旧 Beta 正文和新版异机恢复的正文都可能缺少可核验的来源，当前官方开关无法区分两者。玩家可以先阅读或复制原稿，再明确重新生成。单独导入同名书、同版本书或还原官方开关均不会给旧正文补发来源凭据。

真实供应商和实体设备留待负责人验收。合流时需保留正式草稿 CAS、实例检查、候选与来源同事务写入，以及回执重放路径。此次测试覆盖当前 Beta 的默认和文学预设。更新客户端时应刷新仍在运行旧版代码的页面。
