## 新旧架构

| 数据 | 原有行为 | 本次处理 |
| --- | --- | --- |
| `saves` / `drafts` | 唯一正式状态及候选 | 不改变格式；确认回溯后原子替换正式状态并建立绑定新行动的草稿 |
| `turnUndo` | 最多五份、64 MiB 回合前完整快照 | 原样复用，不复制另一套自动历史；列表从 `saveControls.records` 读取描述信息 |
| `saveControls` | epoch、实例身份、撤回链 | 描述项增加可选小摘要；旧项缺少摘要仍能读取。确认回溯创建新 epoch、新实例，清空旧链 |
| `turnReceipts` | 正式提交幂等回执 | 确认回溯事务内清除当前存档的全部旧回执，其他存档不动 |
| `historyMetadata` | 无 | 独立版本 1 元数据，复合主键 `[saveId,id]`、saveId 索引 |
| `historyPayloads` | 无 | 独立版本 1 完整正式状态载荷，同样复合主键，不保存候选、撤回链或请求 |

IndexedDB 连接版本 **4 → 5**，升级事务只增加两个 store，不重写旧记录。原有 versionchange 处理关闭旧连接；旧 V4 程序不能重新打开 V5 数据库。因此发布后不能直接降级到旧客户端继续写库。GameState 和 IndexedDB 版本是两件不同的事。

`history-saves.test.ts` 从真正的 V4 五个 store 建立旧库，再用新版 Repository 打开；核对全部旧记录保持一致、旧撤回节点能预览、旧 V4 reopen 被拒绝。没有清空旧撤回历史作为迁移手段。

## 节点与只读预览

自动节点表示 **结算前已经完成的回合**。例如当前完成第 7 回合，五个恢复点是第 2、3、4、5、6 回合结束，不是第 3～7 回合结束。开局不伪造第 0 回合恢复点。

列表不读取 `historyPayloads`，也不读取 `turnUndo` 的完整 value；只读元数据及自动链 key。它仍会读取、校验当前正式状态以核对活动时间线，不宣称完全不读取当前 GameState。旧自动描述项没有日期摘要时明确标为选中后读取真实时间。

选择节点后只解码该节点。预览具有明确的「只读历史」提示，可切换历史章节、人物、经济及现有世界资料；不挂载可自动运行维护任务的 GameScreen，也不提供 NPC 管理写入回调。正式存档、草稿、撤回链保持原样。预览只保存一个当前节点及用于确认的内存快照，不长期缓存全部收藏。

手动收藏使用独立 UUID，不按名字覆盖，不设置十份或二十份上限（每页显示 20 项仅为分页）。名称可改；删除必须确认。保存对象始终取 Repository 当前已正式结算的 GameState，未结算正文和断点片段不进入收藏。开局尚未正式结算时拒绝收藏。

## 原子回溯与费用边界

`HistoryRepository.preview()` 返回内存中的一次性确认令牌，绑定存档、所选原始载荷、当前正式状态、草稿和控制记录。令牌不写入浏览器存储；显示用 state 被调用方修改不能改变权威恢复源。

1. 输入行动并点发送，只打开覆盖警告，不写库、不请求模型。
2. 取消只关闭警告，原未来回合、五份恢复点、草稿完全保留。
3. 确认后先取得现有同存档 session 与 **必需的 Web Lock**。缺少 Web Locks 或其他标签持锁时保守拒绝，不发请求。
4. 解码和严格验证选中节点；进入覆盖七个 store 的单一 IndexedDB 读写事务，再比较当前正式状态、草稿、控制记录和所选原始载荷。不能只靠 revision：未提升 revision 的记忆维护变更同样令确认失效。
5. 正式恢复全部历史世界；revision 取「当前版本、收藏版本」较高者再加一；更新真实保存日期。journal 的既有来源版本不改写。清空全部旧自动恢复点及当前存档旧回执；创建新 turnId、草稿版本、新 epoch、新 instanceId；持久化本次行动。手动收藏不删除。
6. 事务成功后，UI 通过一次性内存授权调用原有正常自动流程。普通读取、刷新、离开预览不会重建该授权；离开窗口后完成的事务不会偷偷启动生成。
7. 模型失败时保留已确认的新基线与草稿，由现有失败回填、修改重发及安全诊断处理。没有自动补发、额外 AI 阶段或静默回滚到旧未来。

并发确认最多一个成功。旧草稿、旧提交和旧总结沿用现有实例／epoch／CAS 校验而失效。任一数据库写入失败时整个恢复事务回滚，不能先清掉旧恢复点再丢失正式状态。若保存成功后页面中断，新草稿仍合法，但刷新不自动付费。

恢复根不继承任何旧 Undo。新回合结算后重新积累最多五份，不能撤回至新根之前。手动收藏来源实例与当前不同，或来源回合已不在当前 journal 时标为「旧时间线收藏」；仍可再次明确确认恢复，不自动合并。

## 压缩、容量与备份

载荷 envelope：`version:1`、`encoding:gzip|json`、UTF-8 原长度、原文 SHA-256、ArrayBuffer。使用无损 gzip；压缩不可用或无节省时保存原 JSON。真实压缩错误导致本次保存失败，不覆盖已有节点。读取验证长度、摘要、存档身份、SHA-256，再使用正式迁移／Schema 校验。

单节点导出另校验完整标准备份文件不超过原导入器的 256 MiB 上限（包含外壳与摘要），超限明确失败并保留收藏，不能生成随后无法导入的“成功备份”。

单份未压缩内容设置 **256 MiB 安全读取上界**，用于防止损坏载荷膨胀，不是收藏数量限制。流式解压在超过声明长度时立即终止。gzip 解压 API 缺失时明确拒绝读取该节点，保留原数据；不会伪造空存档。

专用 Worker 承担编码、gzip、校验、解码和备份序列化；任务完成／失败／120 秒超时后终止。无 Worker 的浏览器拒绝新建收藏和导出；仅允许 ≤2 MiB 的小记录读取。没有把大任务用 Promise/setTimeout 伪装为后台工作。IndexedDB 结构化克隆、当前状态验证和原子 CAS 比较仍有主线程成本。

显示的是两条记录 envelope 的 UTF-8 字节与实际编码 buffer 之和，不包含 IndexedDB 引擎页、索引等内部磁盘开销。浏览器 `storage.estimate()` 单独标为估算，80% 配额提示导出和清理；QuotaExceeded 原子失败，不自动淘汰手动收藏。

普通单档／全档备份格式不变，**不包含手动历史收藏**；管理页与全档导出提示已经说明。每个合法节点可单独导出标准 `.heijin.json`，不含草稿、撤回链及其他收藏；原导入功能可恢复。导入覆盖正式存档时保留手动收藏，由新实例将其标记为旧时间线。删除可读存档的确认明确包括全部收藏，删除事务清理两 store，不留下孤儿。不可读主档若仍有关联收藏（含残留元数据或载荷），禁止删除，详见本轮 P1 返修记录。

当前正式父存档不可读时，暂不开放历史管理入口；损坏收藏元数据只显示不可读并保留数据，不能伪造导出。此类情况应先保留浏览器原始数据并由维护者恢复，不能把浏览器临时存储当作永久备份。

## 限制及复审重点

1. 浏览器存储仍可能被用户／系统清理；“永久收藏”意为不随游戏自动轮换，不代表云备份。必须导出重要节点。
2. 256 MiB 解压上界以下的极大状态仍有显著内存需求；本轮实测最大约 9.25 MB。未声称 256 MiB 在手机实机可流畅运行。
3. IDB 克隆、完整 Schema 和 CAS 比较仍在主线程有成本；测量显示存在百毫秒间隔，未来可继续研究传输和验证成本，不通过削减世界数据换取数字。
4. 暂无 Safari/WebKit、Windows、真实手机或真实收费模型验收。Mock 只证明调用边界与协议执行。
5. IndexedDB V5 需要旧标签关闭；不能部署后把应用回退到只支持 V4 的代码并继续写库。
6. 有意不新增手动收藏整体打包协议；单节点标准导出已实现。极接近载荷大小上限的节点，加入备份外壳后可能超过原导入限制，此时拒绝导出，不伪造成功；不会自动拆分或删除内容。正式父存档损坏及历史载荷损坏的维护恢复仍需单独工具。
7. 原正常三阶段测试开启 Variables / World；合流后增加纯小说模式一次 Story 结算测试。#180 的实现完全来自 main，本 PR 不改其逻辑。为精确统计三阶段请求，夹具关闭自动记忆总结；原总结机制与费用限制未改，迟到写入另由 epoch 回归覆盖。
8. 新回溯根丢弃全部旧自动链，不支持 Redo；手动收藏独立保留，是唯一可供以后再次明确选择的旧时间线节点。

## 十三代目复审返修：损坏主档的收藏删除保护

审查：[review-5930250690](https://github.com/WJT111222/HeiJinWangChao/pull/181#pullrequestreview-5930250690)。返修前 HEAD `1d070559e17fbc9a472cce0df0639cae768031f2`，开工重新 fetch 后 PR 和 main 均未变化（main `4ef1093ed82e05ce76583ab3ba7cafbdf61249a4`）。本次继续原分支，无其他 PR 混入。

**根因**：`exportRaw()` / `serializeRawSave()` 的原始抢救 V1 文件只包含旧五表，无法表示新收藏的压缩 ArrayBuffer；原 `deleteUnreadable()` 却清掉关联的两张收藏表。用户导出后删除会永久丢失未包含在文件中的收藏。这是实际数据丢失问题，不是仅提示不完整。

**选择审查明确允许的保守阻断方案**，本轮不引入另一套备份格式：

- `deleteUnreadable()` 在原七表 readwrite 事务内，按真实物理主键检查两个 `saveId` 索引。任一元数据或载荷存在即返回固定 `HISTORY_RECOVERY_REQUIRED`，在任何删除前中止。孤立载荷、损坏元数据同样保护；索引读取失败也按失败处理，不假装空库。
- 检查与删除共享事务，其他标签不能在检查后插入一条将被静默清除的收藏；不依赖 UI 的旧列表或下载完成标志。
- PC 卡片、手机车票、删除确认及下载反馈明确标注「原始数据导出不包含手动历史收藏」。已有 V1 原始导出仍可抢救主档五表，**下载成功不解锁删除**。
- App 仅针对该固定安全错误显示明确的保护原因；其他错误仍使用原通用安全文案。未打印原始资料、异常堆栈或凭证。
- 没有收藏的不可读存档仍可按原流程删除；可读存档的明确删除、正式导入／导出、普通五回合撤回及时间线覆盖机制不变。
- 若玩家已经保存了合法标准备份，可以通过既有明确覆盖导入修复主档；导入保留全部收藏，恢复后可正常逐节点导出。测试使用损坏前保存的真实节点备份，不把不完整原始 JSON 伪装成可恢复收藏的文件。
