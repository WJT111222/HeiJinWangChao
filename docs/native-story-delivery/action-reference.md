# 原生 Story 的当前行动与工具交付

本轮恢复了 `e593dcbc` 的资料搬运范围。玩家输入、主角与世界状态、人物索引、开局档案及近期与召回记忆随真实内置脚本进入 `wave_context_reference.description`。普通消息保留原生规则、时间预检、摘要与人物知识约束、格式提醒，以及指向当前行动的说明。模型可以从资料中读取行动；是否确实按行动写作，需要另行评估。

## 最终 HTTP 对照

使用同一个合成开局、同一个草稿及仓库询货行动，运行各版本的生产构建、脚本 iframe 和正式生成入口，截取发给 Mock 上游的最终 HTTP JSON。A、B 是独立实验构建。三种方案共用原版资料分区和相同的交付检查，生产只保留 C。

| 版本或实验 | 当前行动在资料工具内 | 末条普通消息的定位 | 资料说明字节 | 整个请求字节 |
|---|---|---|---:|---:|
| 原始参考 `e593dcbc` | 是，最后一项 | “最新的真实用户输入” | 4,367 | 94,424 |
| 上轮 `33558910` | 否 | 直接附上行动全文 | 1,537 | 94,126 |
| A，只补资料记录 | 是，附回合、草稿版本和来源 | 原脚本用语 | 4,490 | 94,579 |
| B，只补普通消息引用 | 是，最后一项 | 明指末项的 `PLAYER_ACTION` | 4,367 | 94,552 |
| C，二者结合 | 是，附回合、草稿版本和来源 | 明指末项及其归属字段 | 4,490 | 94,735 |

表内是 OpenAI 兼容、非流式样本的 UTF-8 字节，不用于估算计费。与原始参考相比，C 的普通消息仍是 28 条，作用域标识使工具说明增加 123 字节，完整 HTTP JSON 增加 311 字节。对四协议 JSON/SSE 的八组请求逐字段比较后，原有上下文可无损重组；两个工具的名称、schema、说明头和输出工具的完整交付段均保留。普通消息中仅最后的读资料提示与原始参考有区别（本组样本的开局时钟已确定）。模型配置、温度 0.25、最大输出 8192 以及各协议的自动工具选择相同。Gemini、Anthropic 仍使用各自原生的工具声明格式。

## 为什么采用 C

原脚本的 `splitContext()` 按标记分离资料，`transformRequest()` 把原消息按顺序序列化到工具说明中，再追加 `READ_INSTRUCTION`。原始参考实际上已把行动置于末项。歧义来自说明只说“最新的真实用户输入”，而历史也可能包含玩家言行；游戏的时间预检还可能有 `actionKind: none`。源码可以证明这些内容同时存在，无法证明某个模型曾因此选错。工具说明过长、渠道截短说明、模型忽略工具都是尚未取得真实轨迹的可能因素。

A 让资料记录可核对，B 让普通消息可导航，C 同时提供这两点。改动限于王朝适配层，原脚本及其 `DESCRIPTION_HEADER`、`waveOutPrepare()`、`buildControlPrompt()` 和响应还原逻辑继续使用原版本。普通消息保留“无需调用资料工具”和原输出工具指令。工具中的资料仍遵循系统规则及人物权限。此选择基于字段可定位、归属可校验和脚本兼容性；Mock 没有测量三种写法在真实模型上的优劣。

- 资料末项的 `CURRENT_TURN` 随冻结草稿写入 `turnId`、`turnKind`、`draftRevision` 和来源 `draft.userInput`，旁边的 `PLAYER_ACTION` 保留原值，包括空行动和 JSON 转义后的特殊字符。重新生成使用本次有效的草稿版本。缺草稿的只读预览明确标为预览，正式发送要求绑定草稿。
- 待定开局还有一个副本 `OPENING_TIME.playerPreference`。本次将它随开局背景搬入工具，普通消息仍保留开局时间政策和输出契约。
- 正式请求在脚本钩子执行之前留取整个待搬运数组，在转换为厂商 HTTP 格式前核对工具说明末行是否包含相同序列及完整内容。缺声明、缺背景、行动或回合不符会在传输前失败。既有单次 fetch、真实结束、工具参数对账、Story 校验和草稿事务继续生效。

对应实现见 [nativeDelivery.ts](../../src/presets/nativeDelivery.ts)、[composer.ts](../../src/prompts/composer.ts)、[runtime.ts](../../src/services/ai/runtime.ts) 和 [wire.ts](../../src/presets/tavern/wire.ts)。

## Mock 验证口径

开局用仓库询货行动，普通回合用博物馆核对展品行动，并保留相反的仓库历史。受控响应器只从实际 HTTP 工具资料的末项选择相应故事。普通回合首次请求收到合成供应商错误，随后由玩家显式重试。检查两次发送的行动、回合及相应草稿版本；每次点击只有一次传输。分别检查真实脚本的 `complete/restored`、严格正文校验、候选保存，以及从 IndexedDB 读出的逐字正文。两组正文分别为 11,845 和 25,205 个字符；三种支持参数增量的协议按每片最多 127 个码点返回，Gemini SSE 使用完整参数快照。此过程验证客户端提供了足以区分两种行动的资料。

隔离矩阵另行测试普通正文、纯文本标记、错误工具、错误参数名、损坏参数、上限、上游错误、无结束帧及读取异常。即使故事标签合法，未经约定工具交付也会被拒绝。反之，回包使用正确工具、标签合法但剧情跑题时，现有结构校验仍可通过。后者必须计入行动遵从失败。取消、重生成失败和切档回归继续检查请求次数、原候选以及正式存档版本。

候选矩阵实跑 92 次，每次传输一次：正常与工具前空白两组各 8 次完整保存，8 个语义反例也通过结构校验，其余 68 次均拒收。另有 8 次主动取消和 4 次 SSE 读取异常，均未新增候选。这些是预设输入的行为分类，不能作为真实渠道的成功率。

浏览器回归见 [生产构建与双端用例](../../e2e/peinture-settings.spec.ts) 和 [宿主与存档保护](../../e2e/tavern-assistant.spec.ts)。

## 真实渠道验收

优先复用已有失败尝试的脱敏诊断。工具名称、是否存在完整资料与行动字段、真实结束原因、还原、严格校验与候选保存状态能定位客户端看得见的环节。缺少中转或上游证据时，无法证明模型实际收到并读过完整 description。

如获付费测试授权，可在同一存档副本、同一回合用一个只有当前行动才指定的目标和物品，并让历史指向另一个合理目标。每组配对固定行动、渠道、模型、采样、推理、篇幅、预算和流式设置；随机化原始方案与 C 的运行顺序。先做一对以检查路径，如需区分定位字段和普通引用的贡献，再在批准的预算内加入 A、B。评审者在不知道版本的情况下核对剧情是否回应当前动作、对象和地点。按渠道分别报告样本数：

1. **行动遵从**：可判读剧情中正确处理当前行动的次数，同时列出跑题和无可判读剧情的次数。
2. **长文交付**：所有发起尝试中，收到完整且可核对的工具正文的次数；另列经过 Story 严格校验并保存候选的次数和各失败原因。

一次成功只能说明当次交付路径。渠道若删除工具说明，或模型完全忽略说明，当前设计无法保证行动可见或被执行。本轮没有真实模型调用或真实遵从率、交付率结论。
