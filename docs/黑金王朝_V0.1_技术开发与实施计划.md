# 黑金王朝 V0.1｜技术开发与实施计划

**文件性质：** 面向 Codex 的工程实施基线 · 可执行开发任务、边界与测试  
**版本：** 0.1.0-tech · 2026-10-18  
**配套文件：**《黑金王朝 V0.1｜游戏设计规范》  
**状态：** 本文所列数据结构、目录、技术栈与接口样式为【建议实现】，除非标注【确认需求】；如 Codex 发现更小而可靠的实现，可先说明差异再修改。不得擅自改变已确认游戏规则。

## 00｜致开发者：先读这一页

### 0.1 要交付什么

目标是一个可在浏览器正常游玩的**单人 AI 文字开放世界 V0.1**。项目以“现代中国城市 + 自由角色 + 开局重大变故”为内容底座。主游戏拥有三阶段 AI 流程，**但开局与普通回合使用六组独立主提示词**。首版应能创建多存档、稳定生成正文、管理变量、推动场外世界、查询记忆、处理时间与失败恢复。

### 0.2 不要擅自做的事【确认需求】

- **不要**修改上游／参考项目《墨色江湖》仓库；它仅供研究和参考。新游戏新建独立项目。
- **不要**直接复制参考项目大段代码或提示词，未核对其许可证、归属与可复用范围前只借鉴架构。
- **不要**引入额外的 NPC 独立长篇 AI 阶段、Lorebook 配置器、传统 RPG 属性、通用世界编辑器或设置项大爆炸。
- **不要**把三阶段拆成“每组变量都额外调用一次模型”：变量分组是**规则与 Schema 分组**，不是 API 调用倍增。
- **不要**让流式片段、失败重试、正文重新 Roll 引发已提交数据的重复修改。
- **不要**把场外秘密展示在普通玩家的世界面板、事件时间轴和流式日志中。

### 0.3 三种标记

- **【确认需求】**：源自双方定稿，原则上必须实现。
- **【建议实现】**：为降低复杂度提供具体工程方案，可提交替代设计说明。
- **【待核验】**：需实际复查参考源码、选定技术栈或运行测试才能锁定。

## 01｜推荐系统边界与目录【建议实现】

推荐前端 TypeScript，独立业务核心，不让 React/Vue 等 UI 组件直接修改游戏对象。是否采用 Vite、React、IndexedDB、Dexie、Zod 等库以初始化环境为准；**不得把候选技术栈当成产品需求**。

  ui/
    game/                  三栏主界面、工作流面板、正文流

    panels/                NPC／势力／地图／物品／世界／历史／记忆详情

  domain/
    protagonist/ npc/ items/ economy/
    organizations/gang/
    organizations/government/

  workflows/
    turnCoordinator.ts      单回合编排、重试、草稿与提交

    variableStage.ts        变量阶段，按开局／普通选主提示词

架构重点是**数据层、提示词组装、AI 工作流、UI 展示四者分离**；相同一条游戏状态不应由多个 React 组件各存一份作为真值。

## 02｜核心数据模型【建议实现；字段含义为确认需求】

### 2.1 单存档状态

```ts
interface GameSave {
  schemaVersion: number;
  saveId: string;
  title: string;
  createdAt: string;                 // 真实世界存档创建时间
  updatedAt: string;
  turnNumber: number;                 // 已正式结算的回合数
  worldClock: string;                 // 游戏世界统一时间，带本地时区语义
  protagonist: Protagonist;
  npc: Record<string, NPC>;
  items: Record<string, ImportantItem>;
  economy: Economy;
  organizations: Record<string, Organization>;
  map: MapState;
  events: Record<string, WorldEvent>;
  tasks: Record<string, WorldTask>;
  memories: MemoryState;
  timeline: TimelineEntry[];
  journal: TurnRecord[];              // 完整回合正文永久归档
  revision: number;                   // 乐观锁、回合提交版本
}
```

一个正式提交的 `GameSave` 应与该回合所产生的事件、记忆、时间线处于相同修订版本；从失败阶段临时结果生成的内容不得进入正式 `revision`。

### 2.2 主角与装备引用

```ts
interface Protagonist {
  id: string;
  name: string;
  age: number;
  gender: string;
  appearance: string;
  personality: string;
  background?: string;
  profession: string;
  skills: string[];                   // 自然语言专业技能，无等级
  healthText: string;
  emotionText: string;
  publicStatus?: string;
  legalStatus?: string;
  locationId: string;
  currentWear: {
    topItemId?: string;
    bottomItemId?: string;
    shoesItemId?: string;
    accessoryItemIds: string[];
    primaryWeaponItemId?: string;
    secondaryWeaponItemId?: string;
    currentVehicleAssetId?: string;
  };
}
```

资产与物品只在各自实体表中存一份，主角穿戴栏保存引用。展示时未装备字段显示“无”；不能因一个道具换槽位就新增一份实体。主角法律状态、职业经验等为描述性字段，不推断拥有机构级权力。

### 2.3 普通与特殊 NPC

```ts
type NPCKind = 'ordinary' | 'special';
interface NPC {
  id: string;
  kind: NPCKind;
  name: string;
  identity?: string;
  background?: string;
  appearance?: string;
  temperament?: string;
  locationId?: string;
  onScene: boolean;
  affinity: number;                   // [-100, 100]
  relationshipText: string;          // 爱／亲情／尊敬／敌意等真实关系
  healthText?: string;
  activeGoals?: string[];
  memories: NPCMemory[];
  privateKnowledgeRefs?: string[];
  lastInteractionAt?: string;
}
```

**建档规则【确认需求】**：变量管理仅为本回合实际登场／参与互动，且未来有长期接触可能的 NPC 新建档案；路过的店员可暂不建档。初始同伴固定为特殊 NPC。场外动态世界可以更新既有 NPC 任务，不得把在场 NPC 误当离场者再次行动。人物记忆必须带有合理的知晓来源。

### 2.4 物品与经济

```ts
interface ImportantItem {
  id: string;
  name: string;
  category: string;
  quantity: number;
  ownerRef?: string;                   // 主角 / NPC / 组织
  locationId?: string;
  conditionText?: string;
  itemDetails?: Record<string, unknown>; // 分类专属字段
  createdByTurnId?: string;
}
interface Economy {
  cash: number;
  onlineBalance: number;              // 跨平台统一可用电子余额
  incomes: Record<string, IncomeRecord>;
  debts: Record<string, DebtRecord>;
  properties: Record<string, PropertyAsset>;
  vehicles: Record<string, VehicleAsset>;
  otherAssets: Record<string, AssetRecord>;
}
```

货币仅以人民币为本世界默认结算单位，允许资产估值与实际余额分离；未来跨国资产或其他币种需要明确汇率和转换记录，V0.1 不必开发浮生境的动态货币引擎。`onlineBalance` 是统一可用金额，**不能把账户间内部转账当成新增收入**；收入来源、债务到期、抵押和车辆购入详细账目独立保存。

### 2.5 势力：判别联合而不是全字段通用

```ts
type Organization = GangOrg | GovernmentOrg | CivilOrg | BusinessOrg;
interface OrgBase {
  id: string;
  name: string;
  kind: 'gang' | 'government' | 'civil' | 'business';
  description: string;
  protagonistRelation: string;       // 不强制数字、阶段枚举
  relationHistory: string[];
  keyNpcIds: string[];
  currentTaskIds: string[];
}
interface GangOrg extends OrgBase {
  kind: 'gang'; territoryText?: string; funds?: number;
  powerText?: string; industries?: string[]; internalStatus?: string;
}
interface GovernmentOrg extends OrgBase {
  kind: 'government'; jurisdictionText?: string;
  lawfulPowers?: string[]; cases?: string[];
  enforcementCapacityText?: string; publicTrustText?: string;
}
interface CivilOrg extends OrgBase {
  kind: 'civil'; missionText?: string; supportersText?: string;
  membershipText?: string; activities?: string[];
}
interface BusinessOrg extends OrgBase {
  kind: 'business'; sectors?: string[]; assetsEstimate?: number;
  liquidityEstimate?: number; ownershipText?: string;
  operatingStatus?: string;
}
```

四个 Schema 的详细字段清单可以在实现时局部扩展，但**不能为了代码统一把官方机构强行加上黑帮地盘与组织资金等字段**。组织关系自由文字 + 变化缘由是共通要求。每类组织分别绑定管理提示词，不代表增加模型调用次数。

## 03｜双模式 × 三阶段提示词架构【确认需求】

### 3.1 六组主提示词与职责

| 主提示词 ID（建议） | 生效时机 | 输出目标 |
|---|---|---|
| `opening.story` | 新游戏首回合正文 | 动态灾难开局 + 摘要 + 变量指导 + 可选行动建议 |
| `opening.variables` | 首回合变量 | 初始化主角／在场重要 NPC／初始资产物品和场景状态 |
| `opening.world` | 首回合世界 | 初始化相关组织、场外 NPC、未来任务与世界事件 |
| `regular.story` | 普通回合正文 | 连续剧情 + 摘要 + 变量指导 + 可选行动建议 |
| `regular.variables` | 普通回合变量 | 根据已发生正文生成结构化变更指令 |
| `regular.world` | 普通回合世界 | 推进场外任务、处理事件、安排可见线索与结案归档候选 |

**切换原则**：新建存档首个回合使用开局三组；首回合完整确认后切换普通三组；读取存档不得因为 `turnNumber=0` 但已存在开局草稿而重新初始化。判断依据应包含回合 `kind` 和完成状态，而不是只看 UI 页面位置。

### 3.2 一组变量绑定一组提示词

每个变量模块至少有：① `schema` / 校验器；② 创建或初始化协议；③ 常规更新协议；④（如需）场外行动协议。下面是概念级模块清单：

| 变量组 | 初始化／更新规则 | 场外规则 |
|---|---|---|
| 主角 | 身份、职业、能力、健康、位置、装备和社会状态 | 不允许 AI 代主角决策 |
| 普通 NPC | 何时建档、好感变化、在场互动、记忆来源 | 离场日常行动、相关计划 |
| 特殊 NPC | 深档案、重要记忆、稳定目标 | 独立计划、关系发展 |
| 重要物品 | 实体唯一性、归属、数量、装备引用 | 仅与任务相关的离场转移 |
| 经济资产 | 七分组、账户变更、资产债务记录 | 到期提示、场外经济事实候选 |
| 黑帮势力 | 地盘、资金、实力、内部分歧与主角关系 | 组织行动与时间成本 |
| 官方势力 | 职权、管辖、案件、调查与主角关系 | 法定程序与办事时序 |
| 民间组织 | 宗旨、活动、成员、公共影响 | 行动与社会传播 |
| 商业集团 | 股权、经营、产业、商业关系 | 经营决策与事件时序 |

模块可以只在相关阶段与相关对象存在时装入对应规则；不会因为有 9 个子组而每轮调用 9 次 AI。

### 3.3 运行时提示词组装【建议实现】

```text
玩家选择的设置（7 项）
  + 当前阶段主提示词（六组取其一）
  + 共享规则（权限、叙事真实、信息隔离、结构协议）
  + 仅相关变量组专属规则
  + 主角／在场 NPC／相关组织数据
  + 最近 N 回合完整正文 + 分层摘要 + 关联回忆
  + 相关未来事件／当前输入（按可知权限）
  = 发给对应模型的消息包
```

提示词注册用稳定 `id`、用途、适用 `stage`、优先级、默认启用条件、文本模板；互斥模块只取一份，不在全局字符串里靠关键词删除其他规则。必须能在调试日志里检查**最终实际注入的模块 ID 清单**与计算后的长度，但秘密内容不能流入普通玩家可见日志。设置组装与用户可编辑文本严格分离。

### 3.4 七项提示词设置与程序开关的分界

叙事人称（3 选 1）、剧情风格（目前有“一般”）、正文字数硬最小值、NoControl、自然文风修复、行动选项、真实世界模式，共**七项提示词自定义**。变量管理开关、动态世界开关、超时、校验与自动重试属于**运行设置**，绝不能混算成第八或第九项提示词设置。

关于现有《墨色江湖》的自然文风修复原文与接口打包逻辑，作为参考资料可逐步审阅；**不得在没验证协议兼容与版权许可前原样复制全部提示词输出**。将模块目录作为当前项目独立实现的契约。

## 04｜三阶段数据契约与变量指导【确认需求＋建议格式】

### 4.1 阶段①：正文生成

**输入**：回合起始已提交快照、玩家输入、世界时间与地点、相关对象、可知事件、近期正文和摘要、开局或普通提示词。**输出**：正文、回合摘要、变量指导、可选行动选项。

```ts
interface StoryResult {
  turnKind: 'opening' | 'regular';
  narrative: string;                       // 只这部分计入正文最低字数
  summary: string;
  variableGuide: Array<{
    group: string;
    subjectHint?: string;
    observedFact: string;                  // 发生了什么；不是未来计划
    textEvidence?: string;                 // 正文线索
  }>;
  actionOptions?: string[];                // 开启时 3～5 条
}
```

`variableGuide` 是**建议而不是命令**，不能直接进入状态数据库。例如正文只写“打算买车”，指导却建议“扣款”时第二阶段必须拒绝；不能为了有输出而强制造 NPC 或资金变化。

**流式策略【建议】**：正文增量渲染，结构化结尾分段缓冲；完成后完整解析／验证摘要、指导、选项。若模型输出结构损坏，不把半截文本当已完成回合。正文最低字数依玩家输入数字严格判断，仅统计 `narrative`；无默认百分比宽容。

### 4.2 阶段②：变量管理

**输入**：本回合已完成正文 + 变量指导 + 回合起始快照 + 相关变量组 Schema／提示词。**输出**：有证据的变更提案、被拒绝提案、未能确定的事项。禁止新编情节、替玩家完成尚未发生的动作。

```ts
interface VariableStageResult {
  commands: DomainCommand[];              // 不直接执行裸任意路径赋值
  rejectedSuggestions?: Array<{
    reason: string; reference?: string;
  }>;
  unresolved?: string[];
}
interface DomainCommand {
  commandId: string;                     // 便于幂等去重
  group: 'protagonist'|'npc'|'items'|'economy'|'organization'|'time'|'event';
  type: string;                          // 例：CashChanged / NpcCreated / ItemTransferred
  entityId?: string;
  payload: Record<string, unknown>;
  evidence: string;                      // 正文已发生证据
}
```

运行时执行前由程序验证：实体存在与类型、唯一 ID、归属、金额与数量、槽位、时间不倒退、NPC 在场约束、相关证据；有冲突时拒绝不合法命令并报告或让该阶段重试，不将失败结果部分落库。

### 4.3 阶段③：动态世界

**输入**：阶段②的已验证临时状态（若阶段②失败则用旧快照 + 正文与“变量未完成”标记）、现有任务表、时间窗口、相关场外 NPC／组织协议；不得获得主角未来打算、未授权信息。**输出**：场外行动／事件状态的变更提案、下一步任务、可见线索、重要事件完结候选。

```ts
interface WorldStageResult {
  taskCommands: DomainCommand[];
  eventCommands: DomainCommand[];
  futureEvents: WorldEvent[];
  visibleHooks: Array<{ text: string; revealAfter?: string }>;
  timelineCandidates: string[];          // 事件 ID，必须已经结算
}
```

动态世界不得直接替主角接受邀请或结婚、自动完成玩家交易，也不强制每回合产生帮派冲突。场外已形成但未被主角知晓的消息属于内部状态，**不直接向玩家展示细节**。

### 4.4 建议的输出机制

优先用模型兼容的结构化输出协议；不支持时使用稳定分隔标签 + JSON 结构化分段并做解析。严格分离正文与结构数据，别在流式未结束时执行命令。各模型差异由 `services/ai` 适配器消化，不让下游业务判断“这条消息是不是 Gemini 风格”。

## 05｜回合事务、重新 Roll、重试与双开关【确认需求】

### 5.1 六种关键状态

```ts
type TurnStatus =
  | 'draft_story'          // 已生成正文、可继续 Roll、未正式提交
  | 'story_ready'          // 选定正文与变量指导
  | 'processing'           // 变量／世界阶段进行中
  | 'partial_pending'      // 某启用阶段失败或下游待校验
  | 'ready_to_commit'      // 所有本次启用阶段合法
  | 'committed';           // 原子提交完整回合
```

**【确认需求】两个运行开关可独立关掉**。开关状态在开始一次生成时快照到 `TurnAttempt` 中，本轮不因用户中途切换 UI 而悄然改变已经进行的请求；用户后续显式选择补算时使用新开关配置。

### 5.2 临时态与正式态

```ts
interface TurnAttempt {
  turnId: string;
  baseSaveRevision: number;
  turnKind: 'opening' | 'regular';
  userInput: string;
  useVariableStage: boolean;
  useWorldStage: boolean;
  story?: StoryResult;
  variables?: VariableStageResult;
  world?: WorldStageResult;
  status: TurnStatus;
  stageAttempts: Record<'story'|'variables'|'world', number>;
  invalidatedStages: Array<'variables'|'world'>;
}
```

每次执行均从**同一回合开始时快照**求出一份候选状态；不直接在持久化 `GameSave` 上边流式读边修改。全部必需校验通过后，使用一笔原子事务写入回合及所有副作用。若使用 IndexedDB，需用单事务写入；数据库不支持多表事务时通过单版本快照与原子指针提交模拟。不可出现“正文写成功，扣款写了一半，事件没写入”的破碎版本。

### 5.3 自动三次与手动重新加载【确认需求】

- 阶段请求：首次失败后自动 Roll **最多两次**，合计**最多三次**。每次尝试必须有独立尝试编号与错误记录。
- 阶段②三次全失败：正文不丢；阶段③仍可运行时继续执行，但依据可能不完整，所有世界结果标注“**待校验**”。结束后出现“重新加载变量”。
- 阶段③三次全失败：正文和成功的变量候选不丢；结束后出现“重新加载动态世界”。
- 两者都失败：分别提供手动重试按钮；不重写已经接受的正文。
- 如果阶段①正文三次失败：因为没有可用正文，后续无法运行；保留玩家输入和人物设定，允许手动重试阶段①。
- 手动重新加载执行**失败的阶段**，不是重新创建整个回合；成功后按依赖关系重新验证受影响的下游结果，必要时**只重跑受影响的下游阶段**。

```text
正文成功 ──→ 变量成功 ──→ 世界成功 ──→ 原子提交
              │ 3 次失败       ▲
              ▼                │
          标记待修复 ──→ 世界生成(仅预览／待校验)
              │                │
       玩家手动重载变量 ───────┘
              │
        通过一致性校验 → 如不兼容，重跑世界 → 提交
```

**代价与使用体验**：三次自动重试可能增加 API 成本，UI 要展示“第 1/3、2/3、3/3 次”，无须强制开放次数设置。

### 5.4 重新 Roll 正文与回退【确认需求】

- **重新 Roll 正文**：同回合重新调用阶段①，旧版正文及其变量、世界**候选**全部作废；上一个正式提交存档不变。
- **重新加载阶段**：只修复当前失败／待同步阶段，保持当前选定正文不变；只在确有依赖失效时重新运行下游。
- **回退上一回合**：恢复前一完整 `GameSave` 快照，连同时间、物品、资金、NPC、记忆、任务、时间轴一起回退；必须先显式操作。

### 5.5 双开关的精确定义【建议实现，保留玩家自由】

| 变量开关 | 世界开关 | 本次操作策略 |
|---|---|---|
| 开 | 开 | 常规三阶段，完整合法后提交 |
| 开 | 关 | 正文 + 变量确认后可提交；世界阶段标记“用户跳过”，并非失败，不产生世界副作用 |
| 关 | 关 | 只生成／反复 Roll 正文；允许保存**草稿文本**，不把它伪装为已结算游戏状态 |
| 关 | 开 | 世界可以读取正文和旧状态生成**临时预览**，但变量结果缺失时不直接提交依赖它的世界副作用 |

这里有个真实设计张力：玩家有意长期关闭变量管理时，连续故事正文与世界数据可能不同步。V0.1 采取**保守策略**：未同步正文可保存并随时继续 Roll／补算，但默认不把未同步的草稿作为下一个“已结算世界回合”使用；显示清楚的待同步状态。若测试发现玩家强烈需要完全“纯小说连续模式”，可在后续版本设计单独的叙事存档路径，**不要让实现阶段暗中吞掉数据冲突**。

### 5.6 幂等性与证据链

每笔模型命令必须绑定 `turnId` + `commandId` + 目标实体，程序对同一个命令只可应用一次；同一个故事事实（购车、汇款、建档）不能因为重试出现两条独立副作用。引用旧状态的命令应携带期望版本，版本不符时冲突而不是强行覆盖。生成中显示的是**预览变更**，提交成功后才显示“已生效”。

## 06｜时间与未来事件调度【确认需求＋建议算法】

### 6.1 数据结构

```ts
interface WorldEvent {
  id: string;
  title: string;
  status: 'scheduled' | 'active' | 'resolved' | 'blocked' | 'cancelled';
  startAt: string;                    // 游戏世界时间
  estimatedEndAt?: string;
  locationId?: string;
  actorRefs: string[];
  prerequisites?: string[];
  blockers?: string[];
  visibility: 'hidden'|'partially_known'|'known';
  impact: 'minor'|'significant'|'major';
  resolutionText?: string;
  sourceTurnIds: string[];
}
interface WorldTask {
  id: string;
  actorRef: string;
  goal: string;
  startAt: string;
  dueAt?: string;
  status: 'planned'|'active'|'completed'|'blocked'|'cancelled';
  locationId?: string;
  linkedEventId?: string;
}
```

事件执行时间、行动耗时与等待条件必须有明确锚点，不能以用户系统时钟作为游戏时间。地点与任务状态分开。事件不要求在每个回合发生显著变化。

### 6.2 正文前的事件预检

从当前游戏时间读取尚未完成的事件和任务；对于用户显式“睡到晚上／等三天／直接去机场”等可推定时间窗，扫描时间窗内的重要节点，筛出有可能接触到主角的事件。生成一个**不含不应透露给玩家的内部事件上下文**，只向正文模型注入其所需的现实触发条件和知晓边界。

```text
玩家：上午 08:00 睡到 20:00
时间预检：15:00 有访客到主角家门口
正文：判断敲门是否真实响起、是否足以叫醒、主角知道什么
变量：实际醒来时间或继续睡到 20:00 的最终时间
世界：结算到访或未能联系的后续计划，不重复执行
```

### 6.3 长跨度跳跃【建议实现】

长时间跨度按**重要时间节点**切片推进，而不是对每一分钟模拟。顺序：取得待触发节点 → 检查条件／阻断 → 决定是否可能影响现场 → 交给正文／世界结果 → 标记已处理 ID → 推进时钟。为避免无限事件级联，可限制单次预检节点数量并提示“存在大量待结算事件”，但不得静默丢弃所有后续事件。重复审查同一事件不能再增加一天或再触发一次。

### 6.4 信息可见性

至少区分：内部世界真相、NPC 私有知识、主角已知信息、玩家界面可见内容。系统保存秘密时不代表普通玩家可以看到。世界事件面板、时间轴、流式世界阶段只展示该玩家合理知晓的内容；开发者调试视图需要显式区分并避免默认泄露。

## 07｜记忆体系与归档【确认需求】

### 7.1 分层和持久原文

- **即时**：默认取最近 **10 回合完整正文**进入上下文；允许玩家自由填写 N；变化仅影响注入窗口，不删旧正文。
- **短期**：每回合一条摘要，按参考项目规则聚合。
- **中期／长期**：分批压缩，保留重要人物关系、因果和长期事实；记录来源范围。
- **NPC 独立记忆**：按人物知晓来源建档与总结，不得自动继承主角所有秘密。
- **回忆档案**：永存回合原文、摘要、状态版本与关联对象 ID；按需本地检索历史回合。

参考《墨色江湖》的阈值与压缩批次**实施时需按具体源文件核对**。研究中出现过短期阈值 30、中期阈值 50、NPC 总结阈值 20 的口径，不应凭此推断全部细节已可照搬。保证“原文永久保存”和“上下文只加载相关信息”的分离。

### 7.2 建议存储模型

```ts
interface MemoryState {
  immediateWindowSize: number;         // 默认 10
  short: MemoryEntry[];
  medium: MemoryEntry[];
  long: MemoryEntry[];
  npcSummaries: Record<string, MemoryEntry[]>;
}
interface MemoryEntry {
  id: string;
  text: string;
  sourceTurnIds: string[];
  affectedEntityRefs?: string[];
  visibility: 'player_known' | 'npc_private' | 'internal';
  createdAtGameTime: string;
}
```

建立摘要时不删除 `journal` 原文；压缩结果要有来源范围和失败恢复策略。关于高频事件，可先在程序中保存事实结构再写摘要，避免摘要漏掉债务还款约定等长期条件。

### 7.3 历史时间轴（重要且已完结）

`TimelineEntry` 包含唯一事件 ID、实际结案或事件发生日期、标题、地点、简述、结局、长期影响、相关主角／NPC／组织 ID、关联回合号。**只在事件已结算、影响达到重大标准、玩家合理获知时展示。** 可内部预存“尚未揭示的时间轴候选”，揭示时按原有发生日期插入。索引使用事件 ID 做唯一约束，不因每轮再次总结而重复新增。日常小事不进入时间轴。允许重要家庭、事业、法律事件，不能只记录黑帮冲突。

## 08｜多模型 API、设置与密钥安全【确认需求＋建议实现】

### 8.1 两层配置

```ts
interface ApiChannel {
  id: string;
  label: string;
  protocol: 'openai-compatible' | 'gemini' | 'anthropic' | 'other';
  baseUrl?: string;
  secretRef: string;                   // 不应在可分享存档中存明文密钥
  defaultModelId?: string;
  modelParams?: { temperature?: number; maxOutputTokens?: number };
}
interface ModelRoute {
  channelId?: string;
  modelId?: string;
  inheritFromStory: boolean;
}
interface WorkflowModelSettings {
  story: ModelRoute;
  variables: ModelRoute;
  world: ModelRoute;
}
```

先保存 API 渠道，再给三阶段指定路由。变量／世界可选“跟随正文”，或同渠道不同模型。提供测试连接、模型列表获取失败时手填模型 ID。正文最小字数、提示词开关不混到 API 参数页。模型切换不影响存档已有世界状态。

### 8.2 安全要求【确认的工程必要条件】

从浏览器直连第三方 API 会让密钥存在客户端环境，首版应清楚提示用户保管；**绝不写入游戏存档导出内容、运行日志或分享截图**。如果设置存本地，避免无必要明文持久化；若使用代理服务，则应明确部署与保管成本。前端界面始终遮盖密钥，网络错误不得回显 Authorization 头。用户自行填写的 API URL 必须有可理解的隐私提示。

### 8.3 运行设置与默认值

| 设置 | 分类 | 需求 |
|---|---|---|
| 变量管理开关 | 运行 | 独立可控；默认开启【建议】 |
| 动态世界开关 | 运行 | 独立可控；默认开启【建议】 |
| 超时 | 运行 | 可配置；流式空闲超时与首次响应超时可内部拆分 |
| 自动重试 | 运行 | 固定首次 + 2 次；阶段失败后可手动重新加载 |
| 流式进度 | 运行 | 默认启用；三阶段持续更新状态 |
| 输出协议校验 | 运行 | 必须校验，失败不提交不合法状态 |
| 即时记忆回合数 | 记忆 | 默认 10，自由填写正整数，有合理输入上限提示 |
| 七项提示词 | 提示词 | 与游戏设计文档一致，不额外加层级选项 |

## 09｜UI 组件与状态交互【确认需求】

### 9.1 主界面

左栏独立滚动：时间 → 地点 → 天气 → 环境描述 → 主角状态 → 现金／线上资金 → 穿戴（衣服鞋饰）→ 主副武器／载具 → 其他档案与资产。中间为正文阅读 + 行动选项 + 输入框上方三阶段流式面板。右栏一列直接入口：NPC、势力、地图、物品栏、世界、历史、记忆。点击对应入口**一次打开专属大界面**，不在侧栏手风琴展开，也不先要求切换标签。

### 9.2 工作流面板建议状态

```text
正文生成             ✓ 已完成
变量管理             ↻ 生成中（第 2/3 次）
动态世界             · 待执行

▼ 变量变更预览
  现金               3,500 → 2,700 元（未提交）
  重要物品           新增：合同副本（未提交）

[重新 Roll 正文]    [取消本轮]
```

失败时提供“重新加载变量”或“重新加载动态世界”；如果世界基于缺失变量预览成功，显示“待校验”，而不是展示绿色“已完成正式提交”。事件的隐私部分只能显示“场外行动已更新”等概要信息。

### 9.3 其他界面

- **角色创建**：五步向导，第三页上方约 2/3 城市、下方约 1/3 可选自由背景；预设职业完整介绍与能力说明，允许自定义。返回编辑不清空已填写资料。
- **NPC／势力／地图／物品／世界／历史／记忆**：分别为独立宽界面，关闭后保持正文滚动位置；查看 UI 不触发新 AI 回合。
- **设置**：AI 连接、提示词、记忆、运行四类，提示词恰好七项；运行页有变量／世界独立开关。
- **开发公告**：新公告进入游戏可显示一次，提供历史查看；公告与世界事件完全隔离，优先采用静态版本文件实现。

## 10｜存档、版本迁移与一致性校验【确认需求＋建议实现】

### 10.1 多存档与恢复

每个存档自有世界、记忆、任务、原文和历史时间线；设置中的 API 密钥不随存档导出。对保存的数据添加 `schemaVersion`，变更结构时编写显式迁移。支持保存成功回合快照、查看待同步草稿、失败后恢复单个阶段、回退上个完整回合。

### 10.2 不变量（最低校验）

1. 游戏世界时间不可无依据后退；同一时段的跨日事件不重复增加日期。
2. `cash`、`onlineBalance` 不因一次普通内部转账凭空增加；每次重要扣款有成立的事实依据。
3. 物品 ID 与数量唯一；穿戴项必须指向主角确实持有且兼容的物品；车辆引用指向资产表。
4. NPC 的同一身份不得因为别名或重试重复建档；首次入档须有必要性。
5. 已结算事件不能再次结算；进行中事件按已保存任务时间推进。
6. 组织关系变化有原因，官方机构的权限不凭空扩大。
7. 回忆档案不因压缩删除原始正文；历史时间轴一个重大事件只有一条归档。
8. 失败、预览或已跳过的阶段不能冒充成功提交；副作用只在完整且合法的事务提交时生效。
9. 同一模型命令不得因请求超时、刷新、手动重试而重复执行。

### 10.3 数据变更审计【建议】

每次提交记录 `turnId`、`stageId`、命令 ID、对象 ID、变更前后简要值、合法性结果；普通玩家只看到允许公开的变更，调试详情可以留本地开发日志。不要在审计中记录密钥或大段无法公开的私有 NPC 情报。

## 11｜开发任务拆分与依赖顺序【建议实现】

优先按**可验收的小任务／PR**推进；不要一次要求 Codex 编写全项目。每完成一个阶段都应能运行演示，且有基本测试。建议里程碑：

| 里程碑 | 主要任务 | 完成定义 |
|---|---|---|
| **M0 工程底座** | 新建独立仓库、TypeScript 工程、代码规范、基础路由、静态数据、测试环境 | 可本地启动，存档读写测试通过 |
| **M1 数据领域** | 六大变量组与四类势力 Schema、对象 ID、时间与任务、事件表、原子存档、迁移 | 纯程序测试：购买物品／收入债务／NPC 归属关系稳定 |
| **M2 UI 与角色创建** | 三栏框架、右栏一键大界面、设置四类、五步向导和16职业 | 不连接 AI 也可完成角色创建与导航，刷新数据不丢 |
| **M3 AI 基础** | 多渠道连接、模型路由、流式适配、提示词注册与六组主提示词、七项设置 | 开局与普通回合使用不同提示词，日志可验证实际模块 |
| **M4 工作流事务** | 正文／变量指导、变量命令、世界命令、三次重试、补算、重新 Roll、双开关 | 阶段失败三次仍保留正文，可独立恢复且不重复副作用 |
| **M5 记忆与事件** | 即时10回合／分层压缩、NPC记忆、检索、时间预检、中断、时间轴 | 长跨度时间与历史事实可追踪，不向玩家剧透 |
| **M6 完善与内测** | 运行面板、地图层级、公告、导入导出／回退、错误观测、体验修复 | 完成下文验收清单与100回合压力用例 |

其中 M1 与 M2 可在无模型时并行进行静态原型，但对接前需锁定共享领域契约。Codex 每个任务的提交应包含“修改文件、影响范围、测试方式、未完成项”。

## 12｜自动化测试与人工验收【确认的质量目标】

### 12.1 最低自动化测试矩阵

| 编号 | 测试 | 预期 |
|---|---|---|
| T01 | 玩家选教师、重庆、配偶背景建新档 | 角色资料进入开局上下文，开局同伴不死亡／背叛 |
| T02 | 相同设置生成初始回合、随后进入普通回合 | 六组主提示词调用切换正确，开局限制不污染后续 |
| T03 | 正文“考虑购买摩托车”，变量指导错误建议扣款 | 变量校验拒绝扣款 |
| T04 | 正文“已支付8000买车”，变量阶段两次失败第三次成功 | 只记一次购车与扣款 |
| T05 | 变量连续三次失败，世界生成成功 | 世界结果被标记待校验；可单独重载变量且正文不丢 |

| T08 | 两个运行开关都关闭，反复重新 Roll 3 次 | 所有 Roll 均不修改正式存档，保留最后选定正文草稿 |
| T09 | 变量开、世界关 | 玩家和资产可确认，世界任务不偷偷推进 |
| T10 | 08:00 睡到20:00，15:00 有访客 | 事件可合理打断或错过，时间与任务状态一致 |
| T11 | 跨三天且存在多项事件 | 全部关键事件按时间顺序结算，重新加载不重复触发 |
| T12 | 早期回合重要人物在第100回合被提及 | 记忆检索能定位原文，原始历史未被摘要覆盖 |
| T13 | NPC 私下调查主角且主角尚不知情 | 世界面板、时间轴和玩家日志不泄露调查细节 |
| T14 | 大事件结束，普通买菜随后发生 | 前者进入时间轴一次，后者不进入 |
| T15 | 切换模型与即时记忆 N 值 | 存档不丢；进入 AI 上下文的完整回合数与设置一致 |
| T16 | 回退一回合后重新生成 | 余额、NPC、事件任务、时间、时间轴均恢复一致 |
| T17 | 关闭自然文风修复／行动选项 | 实际注入模块与输出形态正确，无残留旧规则 |
| T18 | 仅把结构化日志和密钥导出测试 | 密钥与内部秘密不得出现在可分享存档或玩家普通日志 |

### 12.2 100 回合稳定性验收

至少覆盖日常生活、资金收入与支出、重要 NPC 关系、两座城市间旅行、时间跳跃、组织场外计划、事件结束入时间轴、人物离场再出现、模型更换和多次失败重试。记录成功率、每次模型请求次数、变量解析失败率、平均等待时间、状态一致性错误与重试恢复率。**100 回合目标是验收场景，不是现有功能保证。**

### 12.3 必须保留的工程诊断能力【建议】

每回合保存**非秘密**诊断摘要：提示词模块 ID、模型路由 ID、输入输出字符数／token 估算、请求耗时、首次／自动／手动尝试次数、解析与提交结果、影响实体 ID。出现问题时可以定位是“正文事实不清楚”“变量指导不准确”“模型结构格式失败”“程序校验拒绝”“世界依赖旧状态”等，不靠猜测。

## 13｜与参考工程的关系及待核验问题

**参考仓库**：`https://github.com/WJT111222/MoRanJiangHu`（《墨色江湖》，用户维护 fork）。其按阶段处理主剧情、变量、世界演变的思想以及分层记忆、模型接口管理与自然文风修复等经验，适合借鉴；但本项目的**双模式六主提示词、分变量组专属规则、历史时间轴、三栏交互、双运行开关**属于《黑金王朝》的独立要求。

实施前需逐项核验而不是凭历史口述臆测：

1. 《墨色江湖》当前 `main` 的记忆阈值、NPC 总结批次、回忆检索行为与调用条件。
2. 原项目的真实提示词装配顺序、不同 API 协议组合及消息角色适配方式。
3. 参考项目相关代码／提示词的许可证与复用约束；未经确认不批量复制。
4. 选定前端与本地持久化方案是否支持原子多对象提交与跨版本迁移。
5. 两个运行开关全部关闭时，玩家连续数个仅正文草稿的可接受交互边界；首版以**草稿不伪装已提交世界**为安全底线。
6. “一般”之外的剧情风格可选文案、首次生成失败后的提示、最低字数不达标时的重试策略与费用提示。

这些开放点不阻止开发骨架，但落地时要在任务记录里列明“待定”并由产品决策确认，不让 Codex私自创建额外设置或改变规则。
