## 阶段 A：格式与字段

### 支持的输入

| 格式 | 识别方式 | 说明 |
| --- | --- | --- |
| 王朝世界书 | `format: "heijin-worldbook"` | 保留书 ID、版本 ID；重算内容哈希，对不上即拒绝 |
| 角色卡 V2 | `data.character_book` 存在，或 `entries` 为数组且条目使用 `keys` / `insertion_order` / `enabled` | 只导入世界书本身，角色卡其余内容不导入 |
| 酒馆世界书 | 有 `entries`（以 uid 为键的对象或数组） | 原文件整体保存为来源数据 |
| 角色卡 V3、NovelAI、Agnai、RisuAI、PNG 内嵌 | — | 明确报“暂不支持导入” |

### 条目字段

酒馆条目的字段与默认值按参照版本整理，规范化后的字段名见 `src/domain/worldbook/schema.ts`，对照表在 `src/domain/worldbook/entryFields.ts` 的 `MAIN_FIELDS`。

- `null` 表示“跟随全局设置”（扫描深度、大小写、完整词、分组评分、Sticky、冷却、延迟），导入时保持 `null`，不替它填值。
- 字段缺失或为 `null` 时取参照版本的默认值。
- 宽松读法只有两种，并且都会记警告：数字字段接受数字字符串（参照版本里它们按数字参与比较和排序）；真/假字段接受 0 / 1（参照版本按真假值判断）。其余类型不符一律报错，整本导入失败，不猜测。
- 文本形式的真/假值（如 `"true"`）不转换而报错：参照版本对它们的判断前后不一致（有的地方当真，有的地方当假）。
- 角色筛选、扫描角色卡文本（6 项）、向量检索、自动化 ID、`addMemo`、`displayIndex` 保留在 `inert` 里，只在原文件出现时才有，王朝不让它们生效。
- 其余未知字段只保存在来源数据里，导出酒馆格式时原样带回。

### 角色卡 V2 的换算

与参照版本导入角色卡世界书的取值方式一致，其中值得注意的几处：

- `selective` 缺省为 `false`（酒馆自己的条目缺省为 `true`）；
- `enabled` 取反得到“停用”，缺失时按停用处理；
- `position`：优先 `extensions.position`，否则 `before_char` 为 0、其余为 1；
- 其余高级字段都从 `extensions` 的下划线命名字段读取（如 `extensions.group_weight`）；
- 书级 `scan_depth`、`token_budget`、`recursive_scanning` 和条目级 `case_sensitive`、`name`、`priority` 参照版本不使用，王朝同样不使用，只记说明。

### 正则关键词

整个关键词形如 `/内容/标志`（标志只能是 g i m s u y）时按正则处理；内容里有未转义的 `/` 时不算正则；内容里第一处 `\/` 还原为 `/`；构造失败时按普通文本匹配。导入时用阶段 B 的安全子集编译一遍，不在子集内的写法记“暂不支持”提示；不拿它匹配任何文本。

参照版本每次匹配都新建正则对象，所以 `g` 不会造成状态残留；`y` 则只从扫描文本开头匹配（扫描文本以分隔符开头，通常永远不命中），导入时会说明。（阶段 A 初版把 `g` 也写成“时灵时不灵”，阶段 B 核对后更正。）

### 宏

`{{user}}` 等宏在关键词和正文里原样保留，导入时不执行。王朝现有的 `{{…}}` 请求校验不变；宏的解析与白名单在正文集成阶段单独设计。

### 身份与哈希

- 导入酒馆或角色卡文件时，每次新生成书 ID 和版本 ID，不按书名判断是不是同一本书。
- 内容哈希：对 `{ metadata, entries, source }` 做确定性 JSON（键按码点排序、无空白）后取 SHA-256。不包含书 ID、版本 ID、来源标记和兼容提示。
- 来源标记一律为 `local`；文件自称 `official` / `workshop` 无效。

### 导出

- **王朝格式**：版本本体原样写出，再导入时内容和哈希都不变。
- **酒馆格式**：来源是酒馆文件时，以原文件为底，保留书级未知字段、`entries` 的形状和键名、条目里的未知字段。来源是角色卡时按完整字段写出新文件，并说明哪些角色卡字段不会出现在酒馆格式里。
- **无损回环（原写法优先）**：原文件里已有的字段，先按导入规则读出它的规范值；与当前条目一致（没有被编辑过）就保留原来的写法——数字字符串（`"50"`）、`0` / `1` 表示的真假、`null`、`uid: null`、`extensions: null` 都原样写回。被编辑过的字段写出新的规范值（例如把 `"50"` 改成 60 后写出数字 `60`）。原文件里没有的字段，只在与默认值不同时写出。内部运行始终使用规范化后的值。（独立审查 P2-1 修正：此前未编辑也会写成规范值。）

### 与参照版本的已知差异（阶段 A）

| 项目 | 参照版本 | 王朝 |
| --- | --- | --- |
| 类型不符的字段 | 多数情况下原样存下，运行时按 JS 宽松规则处理 | 除上面两种宽松读法外一律报错，整本不导入 |
| 重复的条目 ID | 后者覆盖前者或行为不确定 | 两条都保留，王朝内部 ID 加后缀区分，并记警告 |
| 角色卡其余内容 | 属于角色卡本身 | 不导入，也不进入提示词 |
| 角色卡 V3、PNG 等 | 支持 | 暂不支持，明确报错 |

## 阶段 B：触发规则引擎

实现位于 `src/domain/worldbook/trigger.ts`（主流程）、`keyMatch.ts`、`safeRegex.ts`、`timedEffects.ts`、`triggerSupport.ts`。引擎是纯函数：输入书籍版本、可扫描消息、设置、计时状态和随机种子，输出激活条目、插入计划、每个条目的判定原因、预算使用和下一份计时状态。它不读写存档、不联网、不调用模型。

### 扫描流程（与参照版本一致）

1. 所有绑定书的条目合并，按 `order` 从高到低稳定排序；解析正文开头的前缀指令。
2. 逐轮扫描。每轮按排序检查每个尚未激活、本次未掷失败的条目，依次判断：停用 → 触发模式 → 延迟 → 冷却（Sticky 中不受冷却影响）→ 延迟到递归 → 不可被递归 → `@@activate` / `@@dont_activate` → 常驻 → Sticky → 主关键词 → 副关键词逻辑。
3. 本轮候选排序（Sticky 优先，其余保持扫描顺序）→ 分组互斥 → 逐条做概率检定与预算判断。
4. 是否继续：开启递归且未超预算、有可递归的新条目时继续；最少激活数未满足时加深一条扫描；还有未处理的“延迟到递归”层级时进入下一层级。
5. 插入计划按 `order` 从高到低处理，同一位置内 `order` 越大越靠后（越接近生成点）；正文为空、未知位置、Outlet 无名称的条目激活但不插入。

### 关键词匹配

- 扫描文本：最近 N 条消息（每条去掉首尾空白）以分隔符拼接，加上递归缓冲（最少激活数的加深扫描不含递归缓冲）。深度为 0 或负数时不扫描，上限 1000 条。
- 普通文本：不区分大小写时两边转小写后做包含判断；完整词模式下，不含空白的关键词要求两侧是文本边界或非 `[A-Za-z0-9_]` 字符，含空白的直接做包含判断。**对中文基本等同于包含匹配**，与参照版本一致，不另做中文分词。
- 只由空白组成的关键词去掉空白后是空串，会匹配任何文本（参照版本行为）。
- 副关键词逻辑：AND ANY（任一命中）、NOT ALL（任一未命中）、NOT ANY（全部未命中）、AND ALL（全部命中）；未知取值永不满足。
- 分组评分：命中主关键词数；有副关键词时，AND ANY 加上副关键词命中数，AND ALL 在副关键词全中时才加。评分不做宏替换和去空白（参照版本如此）。
- 正则的 `i` 标志：按 ECMAScript 规范的非 Unicode 规则判断——字符先规范化（取 `toUpperCase`；结果不是单个码元时保持原字符；非 ASCII 字符不会规范化成 ASCII），集合里存在规范化结果相同的成员即匹配。要看**整个大小写等价类**，例如 `µ`、`μ`、`Μ` 同属一类，`ǅ`、`ǆ`、`Ǆ` 同属一类，而 `ſ`、开尔文符号 `K` 与 ASCII 字母不同类。首次使用 `i` 时建立一次等价类表（遍历 65536 个码元，Node 22 约 17 毫秒），大小写数据取自运行环境的 `String.prototype.toUpperCase`。全部码元扫描对照 223 万次判断与原生 RegExp 0 处不一致。（独立审查 P2-3 修正：此前只看字符自己的大小写形式，有 51 处不一致。）

### 前缀指令

只有正文以 `@@` 开头时才解析：逐行读，直到第一行不以 `@@` 开头，其后为正文。以 `@@activate` / `@@dont_activate` 开头的行是已知指令；未知指令丢弃；以 `@@@` 开头的行在前一行是未知指令时去掉一个 `@` 再判断，否则忽略。如果每一行都以 `@@` 开头，正文保持原样。只有与 `@@activate` / `@@dont_activate` 完全相同的行才生效。

### 分组互斥

组名按逗号拆分，一个条目可属于多个组；同一组名重复写多次时，每次都算一个成员（参照版本如此，会影响权重抽选）。顺序：有 Sticky 的组只留 Sticky 条目，冷却 / 延迟中的条目移出 → 分组评分（开启时只留最高分，低分条目同时退出该组的抽选）→ 同组已有条目在之前轮次激活则全组作废 → 有优先条目时取 `order` 最高的 → 否则按权重随机抽一个。

组名只作为无原型字典的自有键使用；Outlet 名称同样（插入计划的 `outlets` 是无原型字典，可直接 JSON 序列化，读取时用 `Object.hasOwn`）。`__proto__`、`constructor`、`toString` 等都是普通名称。（独立审查 P2-2 修正：此前 Outlet 名称为这些值时整次触发抛错。）

### 概率与随机数

`useProbability` 为真且概率不是 100、且不在 Sticky 中时掷 0–100 的随机数，掷出值不超过概率即通过；失败的条目本次不再参与。随机数来自调用方给的种子（例如“存档 + 回合 + 第几次尝试”），同一种子结果完全相同，因此**预览与正式生成一致，预览不消耗随机状态**。随机序列与参照版本不同（参照版本用 `Math.random`），规则相同。

### 计时效果：条目修改、版本切换与回溯

- 每条记录挂在“书 ID # 条目 ID”下，带条目指纹（书 ID + 条目全部内容）。记录只作用于**同一键名、同一指纹**的条目。
- 条目被修改或换成另一版本后，旧记录对新内容不生效（旧 Sticky 不让它激活，旧冷却不挡它），旧记录保留到到期为止；期间切回旧内容，旧计时继续有效。
- 新内容按自己的规则激活时，建立自己的 Sticky / 冷却记录，**取代**同一条目下旧内容的记录。每个条目、每种效果只保存一份记录。（独立审查 P2-4 修正：此前旧记录会一直挡住新内容建立记录，直到旧记录到期。）
- 已有同一指纹的记录时（例如 Sticky 期间再次激活）不重新计时。
- 回溯：调用方恢复回溯点保存的整份计时状态，书也回到当时的版本，计时从那里继续。引擎是纯函数，不修改传入的状态。

### 与参照版本的差异（阶段 B，均为有意的王朝适配）

| 项目 | 参照版本 | 王朝 |
| --- | --- | --- |
| 正则关键词 | 用 JavaScript 正则直接执行 | 只运行可验证的安全子集（自写线性时间匹配器，与原生正则做差分测试）；u / v 标志、前后瞻、反向引用、`\p`、八进制、超大重复等不运行，按不命中处理并在结果里列出 |
| 计时单位 | 聊天消息条数；组装请求时就写入状态 | 逻辑消息数：每个成功结算的回合 +2，生成当前回合时 +1（本回合玩家行动）。引擎只返回下一份状态，**只有回合正式结算才保存**；取消、失败、重试、预览都不推进。这是王朝适配语义，不宣称与酒馆所有聊天操作（删消息、编辑、换页等）完全等价 |
| 预览时的计时效果 | 预览（dry run）不读取 Sticky / 冷却 | 预览按真实状态计算，结果与正式生成一致，但不改变状态 |
| 预算 | 上下文 × 百分比，可设上限；“无视预算”的条目不受限制 | 软预算按参照版本：上下文 × 25%，达到即超出。另加**王朝硬上限** = min(合计上限 4096, Story 实际剩余输入预算)，按实际注入总量计算，对所有条目生效（包括“无视预算”的条目），保证不会因世界书导致请求超长；剩余预算为 0 时不注入任何条目 |
| Token 计数 | 模型分词器 | 保守估算：ASCII 每 3 个字符 1、其余字符每个 1.5，向上取整；每条另加 1 计分隔 |
| 递归文本来源 | 本轮所有未掷失败的条目（包括被预算拒绝、并未真正激活的条目）都进入递归缓冲 | **有意修正**：只有本轮真正激活、且未设置“阻止继续递归”的条目提供递归文本。否则被硬上限或软预算拒绝的条目仍能间接激活其他条目，硬上限就失去意义。有回归测试 |
| 多组条目被重复移出 | 第二次移出时误删列表最后一个无关条目（缺陷） | **有意修正**：条目已不在列表中时什么也不做。有回归测试 |
| 同组已激活判断 | 拿已激活条目的完整组字符串与单个组名比较，多组条目可能不被识别 | 照此实现（兼容），有测试 |
| 角色筛选、扫描角色卡文本、作者注释等注入文本 | 参与 | 王朝没有对应内容，不参与 |
| 消息带发言人名字 | 默认以“名字: 内容”参与扫描 | 由调用方决定消息文本格式（正文集成阶段确定） |
| 宏 | 关键词与正文先替换宏 | 默认不替换；提供替换钩子，宏解析与白名单在正文集成阶段设计 |

### 扫描工作量（单次扫描的保护）

安全正则避免了回溯爆炸，但条目多、关键词多、文本长时，合法的匹配本身也可能长时间占用浏览器主线程。引擎因此有一个**确定性的单次扫描工作量上限**：

- **计数方式**：每个操作执行前先按估算代价扣除工作量，扣不下就不执行。计的是操作量而不是时间，所以同一输入永远得到同一结果，预览与正式生成一致。各类操作按实测耗时加权，使 1 个单位在参照机器上约等于或高于 1 纳秒。默认上限 1 亿单位（`maxScanWork`），设计目标是参照机器上最坏约 0.1 秒。（第二轮独立审查后实测更正：大书的普通关键词登记在 40 万个关键词规模下约 2.6 纳秒 / 单位，默认上限下实际约 0.23～0.40 秒；见下文「主线程响应性与 Worker 隔离方案」。）
- **超限时**：立即停止扫描，不进入后续递归轮次。本轮还没判断的条目逐条标为 `scan_limit_reached`（“超出单次扫描工作量上限，未完成判断”），结果的 `work.exhausted` 写明停在第几轮、哪个条目。在准备阶段（登记关键词、计算计时指纹）就超限时不做任何扫描，所有条目标明原因，计时状态原样返回。**不会静默丢弃条目**：每个条目都有判定原因。
- **不留下不完整的候选**：本轮已经选出、**不属于任何分组**的候选照常经过概率和预算处理（它们的结果不依赖没判断的条目）。属于分组的候选无法与没轮到的组员比较，标为 `scan_limit_reached`，说明“同组条目未判断完”。分组处理本身（拆分组名、登记成员、筛选、评分、排序、抽选）也计入工作量；其中任何一步超限，停止**全部**分组处理：正在评分的组标“组「名称」评分未完成”，其余仍在列表里的分组条目标“分组处理未完成”。不会出现只处理了一部分分组、却当作正常结果激活的条目。（独立审查 P2-5 修正：此前分组处理不计工作量，大量组名或重复组名可以绕过上限；评分超限后其余分组照常抽选。）
- **普通关键词一次扫描**：所有普通关键词按大小写模式建成一个 Aho–Corasick 自动机，每段扫描文本只走一遍，同时得到“是否出现”和“是否有满足完整词边界的出现”。代价约为“文本长度 + 关键词总长 + 命中次数”，不再乘以条目数。结果与逐个判断完全一致（有随机差分测试）。
- **其他优化**：同一轮内扫描文本按深度缓存；转小写同一段文本只做一次；计时指纹只给设置了 Sticky / 冷却 / 延迟的条目计算（指纹覆盖条目全部内容，其他条目不可能对上已有记录，结果不变）。

### 主线程响应性与 Worker 隔离方案（待批准）

**实测**（Chrome 153，开发者工具的 CPU 降速模拟手机；没有真实手机数据。默认工作量上限）：

| 负载 | 桌面（1×） | 4× 降速 | 6× 降速 |
| --- | --- | --- | --- |
| 典型：1 本书 300 条 × 5 词 | 11 毫秒 | 38 毫秒 | 55 毫秒 |
| 单本上限：20000 条常驻同组评分 | 80 毫秒 | 208 毫秒 | 360 毫秒 |
| 分组对抗负载（6 种，最慢的一种） | 50 毫秒 | 191 毫秒 | 257 毫秒 |
| 正则 300 条 × 10 个 | 35 毫秒 | 66 毫秒 | 79 毫秒 |
| 单本上限：20000 条 × 20 词，约 1 万字（准备阶段超限） | 231 毫秒 | 967 毫秒 | 1994 毫秒 |
| 8 本 × 20000 条（多书极端，准备阶段超限） | 398 毫秒 | 1838 毫秒 | 3680 毫秒 |

**结论**：分组已不是瓶颈；典型规模在慢设备上也只需几十毫秒。但大书在默认上限下仍是**主线程长任务**——在慢 6 倍的设备上，单本 2 万条约 2 秒，8 本约 3.7 秒。原因有二：普通关键词登记（建索引）在大规模下比权重估计的慢约 2.5 倍；即使权重完全准确，1 亿单位在桌面约 0.1 秒，换到慢 4～6 倍的手机上也有 0.4～0.6 秒。条目越多，排序、建条目、逐条写诊断这些不计费的线性开销也越大。**在当前默认上限下，无法在主线程保证大书场景的响应性。** 调低上限会让大书更早停止（更多 `scan_limit_reached`），只是用功能换响应。

**方案（待批准，本轮未实施，不改引擎）**：

1. **只加一层包装**：新增模块 Worker 运行现有的 `runWorldbookTrigger`。引擎是纯函数、输入可结构化克隆，**不需要改引擎**。项目已有两个模块 Worker（历史编码、预算分析），沿用 `new Worker(new URL(…, import.meta.url), { type: 'module' })` 的写法。
2. **避免每回合复制整本书**：Worker 自己按（书 ID、版本 ID、内容哈希）从 C1 书库读取并缓存不可变版本；主线程每次只传版本标识、消息、设置、计时状态与种子。版本不可变，缓存不会过期。
3. **真正可中断**：取消、超时（例如 3 秒墙钟）或页面切走时直接终止 Worker 并重建。主线程完全不卡，工作量上限仍保留，保证同一输入得到同一结果。
4. **确定性不变**：同一函数、同一输入，预览与正式生成仍一致；单元测试继续直接调用纯函数，另加消息协议与终止测试。
5. **降级**：环境无法创建 Worker 时，在主线程用较低上限运行（例如 2000 万单位），并在诊断里写明“已降级”。不静默。
6. **权重重标定**：同时把关键词登记与建索引的权重按大规模实测上调约 2.5 倍，恢复“1 单位 ≥ 1 纳秒”的设计目标。这会改变现有阈值，需要与 Codex 的复核一起进行，本轮不改。

建议在正文集成（D2）之前完成；D1 的只读预览同样走 Worker。

### 默认设置

扫描最近 2 条逻辑消息；预算为上下文窗口的 25%；所有新增可选世界书合计上限 4096 Token，且不超过 Story 实际剩余输入预算；递归关闭；不区分大小写；不启用完整词与分组评分；最大递归步数与最少激活数为 0（不限 / 不启用）；单次扫描工作量上限 1 亿单位。阶段 B 通过参数传入，阶段 C 起按存档保存。

## 阶段 C1：本地书库

实现位于 `src/services/storage/worldbookLibrary.ts`。独立的附属 IndexedDB `heijinwangchao-worldbooks`，只保存不可变的世界书版本（`releases`，键 [书 ID, 版本 ID]，索引内容哈希、书 ID）、书目索引（`books`）与版本摘要（`summaries`）。结构版本：第 1 版只有前两张表；第 2 版增加版本摘要，升级时从已有版本回填（PR 预览部署可能已建过第 1 版，所以升版而不是原地改结构）。只读访问（触发 Worker）通过 `LIBRARY_READABLE_VERSIONS` 判断能否读取，不触发升级。

- **安装**：校验格式并重新计算内容哈希；同一版本重复安装是幂等的；同一 ID 内容不同则拒绝，绝不覆盖；相同内容、不同 ID（同一文件导入两次）默认返回已有版本，可选另存。
- **读取与列表**：读取时按格式校验，可选重算哈希；列出书目、某本书的全部版本时只读摘要表，不读条目正文（最大规模的书，原来列一次版本在 CPU 降速 4× 下要 1 秒）。
- **安装资源上限**（`LIBRARY_LIMITS`，不信任调用方，独立于导入器再查一次）：单本条目 ≤ 2 万、每条主 / 副关键词各 ≤ 500 个、每个关键词 ≤ 2000 字、每条正文 ≤ 20 万字、确定性 JSON ≤ 8000 万字符（约为文件大小的两倍，覆盖 32 MB 文件）；书库合计 ≤ 1000 个版本、确定性 JSON 合计 ≤ 2.56 亿字符。确定性 JSON 只生成一次：先查大小，超限时不计算哈希。
- **哈希校验策略**：
  - 安装时必验（重新计算，与记录不符则拒绝）；
  - 正式生成读取版本时，由触发 Worker 在**每个 Worker 生命周期内首次载入某版本时**重新计算哈希。在 Worker 里做，不占主线程；不符则该书本次暂停并给出诊断，绝不改用其他版本；
  - 验过的版本只缓存在该 Worker 内，Worker 被终止或重建即失效；
  - 管理界面的列表只读摘要，不验；需要时可调用 `getRelease(…, { verifyHash: true })`。
- **主线程耗时评估**（最大规模：30.6 MB、2 万条，Chrome 153）：导入（解析、校验、哈希）桌面 1.3 秒、CPU 降速 4× 下 5.6 秒；安装（校验、哈希、写入）桌面 1.3 秒、4× 下 5.2 秒，其中确定性 JSON 约占三分之一、SHA-256 约占三分之二。**不能在主线程做**：导入与安装改由 Worker 执行（见「主线程响应性与 Worker 隔离方案」），管理界面只拿回摘要。
- **故障隔离**：所有操作返回结果对象、不抛出；打不开、超时、被阻塞、空间不足、记录损坏都只返回原因。C1 没有接入任何存档流程，书库故障不影响存档。
- **旧版客户端**：只打开主库 `heijinwangchao`，完全忽略附属库（回滚兼容实测见阶段 C 方案）。
- **暂不包含**：存档绑定、计时持久化、回合事务、历史锚点、版本删除、新版备份导入（C2 / C3 另行审批）。
